# Multi-agent support: canonical roadmap root, issue claims, change watch

## Problem

scrummy is safe today for concurrent processes in **one checkout** (lockfile,
`storage/lock.ts`) and for **branch merges** (one file per record). It is not safe for
several agents working across **worktrees** of the same project, because every
worktree/branch holds its own copy of `docs/roadmap/` (see `docs/architecture.md`
§ "What this does not cover"):

- agents in two worktrees each allocate "next id" → duplicate ids;
- an agent does not see another agent's new issue or status change until a merge;
- nothing stops two agents from starting the same issue;
- consuming projects work around this with a manual ritual (every scrummy mutation in a
  fresh worktree off `origin/main`, commit, push to `main`, remove the worktree). It is
  costly, and skipping it once landed roadmap files on an unrelated feature branch
  (easy-nf #327).

Constraints (decided 2026-10-13):

- Agents run on **one machine**, across **several projects and worktrees**.
- **The repo stays the source of truth**: the backlog keeps travelling with the code.
- Needed semantics: **claim/assign issues** and **change notifications**.
- The invariant stays: scrummy runs no git, `gh` or other subprocess
  (`noGitSurface.test.ts`).

## Alternatives considered

| Option | What it is | Verdict |
|---|---|---|
| A. Per-project service | a daemon per repo owns the store; the CLI talks to it over a socket | Solves visibility, but means N daemons for N projects, lifecycle and stale-socket trouble, and it still needs one canonical on-disk place to persist into the repo |
| B. Central machine-wide service | one `scrummy serve` for all projects (HTTP/MCP), store in SQLite or files | Best for cross-project views and push events, but the repo becomes a mirror instead of the source of truth (breaks a constraint). Largest change |
| **C. Canonical checkout** (chosen) | every worktree of a project resolves to **one** roadmap directory on disk; lock, claims and file-watch all work there | Meets every constraint with no daemon. Same machine only, which is accepted |
| D. Collision-proof ids only | keep per-branch copies and use ULID/prefixed ids | Fixes duplicate ids only. No visibility, no claims |

C now. B can come later as an optional layer **on top of** C, because C already gives
each project a single canonical store.

## Approach

### 1. Canonical roadmap root resolution

- New `storage/root.ts: resolveRoadmapRoot(cwd)`. `main()` resolves it once and passes
  it as the `cwd` already threaded through every handler (`cli/registry.ts`). Every
  `storage/paths.ts` helper derives from that value, so this is a single seam.
- Resolution order:
  1. `SCRUMMY_ROOT` env var (explicit override);
  2. `roadmapRoot` in a committed `docs/roadmap/config.json` (relative path to the main
     checkout or to a dedicated "roadmap" worktree);
  3. if cwd is a **linked git worktree**: read the `.git` file → `gitdir:` → `commondir`
     → primary worktree path. These are plain file reads, not a git subprocess, so the
     invariant holds;
  4. otherwise cwd (today's behaviour).
- **Branch guard**: before a mutation, read the canonical checkout's `HEAD` file. If it
  is not `ref: refs/heads/<mainBranch>` (default `main`, configurable in `config.json`),
  refuse with a clear message. This prevents the "roadmap landed on a feature branch"
  class of bug. Escape hatch: `--allow-branch` or an env var.
- The lock is keyed on the resolved root, so all worktrees share one lock with no extra
  work, and ids allocated under it cannot collide.
- `scrummy where` prints the resolved root and which rule picked it.

Committing the canonical checkout stays the job of the human or agent, since scrummy
runs no git. The consuming-project ritual shrinks to "commit the canonical checkout
now and then".

### 2. Claims (assign + lease)

- `Issue` gains optional `assignee?`, `claimedAt?`, `leaseUntil?`.
- Agent identity: `--as <name>` or the `SCRUMMY_AGENT` env var (skills set it to the
  session or worktree name), with a stable fallback such as the worktree directory name.
- Commands, all atomic under the lock:
  - `scrummy claim <id> [--lease 2h] [--steal]`: fails if another agent holds an
    unexpired lease; sets the status to `doing`;
  - `scrummy release <id>`, `scrummy renew <id>`;
  - `scrummy next [--sprint X] [--claim]`: first unclaimed `ready` issue in active-sprint
    order. With `--claim` it picks and claims in one step, which is the key primitive for
    a pool of agents.
- `set-status <id> done` clears the claim. `show`, `show --json` and the viewer display
  the assignee and flag expired leases. `validate` reports expired leases.

### 3. Change notifications

- Extract the fingerprinting in `cli/commands/viewRefresh.ts` into `storage/watch.ts`.
- `scrummy watch [--json]`: long-running; emits NDJSON events (`issue.added|changed|
  removed`, `sprint.*`, `claim.*`) by diffing snapshots whenever the fingerprint changes.
  Agents consume it with Claude Code's `Monitor` tool. The kanban viewer moves onto the
  same module.
- No on-disk event log: diffing keeps the store layout unchanged.

### 4. Skills and docs

- Skills (`scrummy-po`, `scrummy-add-issue`, ...) drop the worktree ritual and call
  `claim` / `next --claim` before starting work.
- `docs/architecture.md`: replace "What this does not cover" with the canonical-root
  model and explain why reading `.git` files is not a git surface. `docs/commands.md`:
  the new commands. README overview.

### Suggested PR split (in order)

1. Canonical root resolution + branch guard + `scrummy where`.
2. Claims (`claim`/`release`/`renew`/`next`) + show/viewer/validate.
3. `scrummy watch` + viewer moved onto it.
4. Skills and docs cleanup, plus the matching update to the user's global CLAUDE.md rule.

## Acceptance criteria

- From any linked worktree of a project, `scrummy show` shows the same backlog as the
  primary checkout, and `scrummy where` explains the resolution.
- Concurrent `add-issue` calls from two different worktrees produce distinct ids
  (multi-process test in the style of `storage/concurrency.test.ts`).
- Mutations are refused when the canonical checkout is not on the configured main
  branch, unless explicitly overridden.
- `claim` is exclusive: of N concurrent `claim`/`next --claim` calls on one issue,
  exactly one wins. Expired leases can be re-claimed, and `--steal` works.
- `scrummy watch --json` emits one event per add, change, remove or claim made from
  another process.
- `noGitSurface.test.ts` still passes: no subprocess anywhere.
- Docs and skills updated. No skill instructs the worktree ritual any more.
